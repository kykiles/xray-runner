# Ревью H10: служба и IPC

Ветка `claude/h10-service` на `9c85454` (c9bba72..9c85454, 11 коммитов). Код не менялся.

## Что запускалось

| Проверка | Итог |
|---|---|
| `go vet ./...` (Linux и `GOOS=windows`) | чисто |
| `go test -race ./...` (Linux) | всё зелёное |
| golangci-lint v1.64.8, собранный go1.26.8 (как `install-mode: goinstall` в CI), Linux и `GOOS=windows` | чисто |
| `TestLiveService` (`unshare -n`) | **не запускался**: в контейнере нет ядра xray, а тесту нужны `XRAY_RUNNER_LIVE_DIR` и вложенный netns. В CI он есть |

Находки 1, 4, 6 и 10 подтверждены временными тестами. Эти тесты лежали во временных файлах `zz_review_test.go`; их удалили, в коммит они не вошли. Остальное найдено чтением кода, уверенность указана у каждой находки.

## Итог

Серьёзные проблемы есть. Главная: проверка `ClientParts` сравнивает ключи с учётом регистра, а ядро разбирает JSON без учёта регистра. Через эту разницу клиент заставляет ядро службы подключиться к локальному unix-сокету с правами root или SYSTEM (находка 1). На Windows лог службы пишется в каталог, который обычный пользователь может создать заранее (2). На Linux split через службу молча перестаёт работать после обрыва соединения (3). Кроме того, на Windows службой может пользоваться любой вошедший в систему пользователь (5).

Сделано хорошо:
- токен возврата 256 бит, сравнивается за постоянное время и привязан к пользователю;
- клиент на Linux проверяет, что сокет держит uid 0;
- клиент на Windows проверяет владельца канала и открывает его с `SECURITY_IDENTIFICATION`;
- у канала `FILE_FLAG_FIRST_PIPE_INSTANCE` и `PIPE_REJECT_REMOTE_CLIENTS`;
- в DACL канала нет `FILE_CREATE_PIPE_INSTANCE`;
- юнит systemd хорошо закручен;
- путь ядра службы жёстко задан (`ownCore`);
- журнал H06 остался в тех же хранилищах: `/run/xray-runner` для root и HKLM для SYSTEM (токен SYSTEM считается elevated), так что совместимость с запуском через `sudo` или от администратора сохранена.

## 1. [Высокая] Проверка `ClientParts` обходится регистром ключа: ядро службы подключается к локальным unix-сокетам

**Где:** `internal/xraycfg/clientparts.go:292-305` (`checkString`), вызов из `checkValue` на строке 280.

**Суть.** `checkString` ловит unix-сокет только под ключами, которые в точности равны `"address"`, `"redirect"`, `"dest"`, `"server"`. Значение `network` сравнивается тоже точно: `"domainsocket"`. Но xray-core разбирает конфиг через `encoding/json`, а тот сопоставляет поля без учёта регистра и с Unicode-свёрткой: K (знак Кельвина) совпадает с `k`, ſ (длинная s) — с `s`. Поэтому `{"Address":"/run/…"}`, `{"Address":"@abstract"}` и `"network":"DomainSocket"` проходят `Validate()` и `AssembleService()` без ошибок. Проверил: `Validate` возвращает `nil`, а `encoding/json` кладёт `"Redirect"` в поле с тегом `redirect`. Проверка ключей по суффиксу (`forbiddenKey`) от этого защищена: ключ приводится к нижнему регистру, а в суффиксах `file`, `log`, `dir` нет букв со специальной свёрткой.

**Почему важно.** Ядро службы работает от root. На Linux у него нет `CAP_DAC_OVERRIDE`, но root — владелец большинства системных сокетов, а `connect()` к сокету не запрещается ни `ProtectSystem=strict`, ни `AF_UNIX` в `RestrictAddressFamilies`. Под угрозой `/run/dbus/system_bus_socket`, `/run/systemd/private`, `docker.sock` и подобные. На Windows ядро работает от SYSTEM. Через IPC это позволяет члену группы `xray-runner` (на Windows — любому вошедшему пользователю) повысить привилегии. Раздел README «Служба» обещает обратное.

**Как исправить:**
- В `checkValue` сравнивать ключи так же, как это делает `encoding/json`: либо отклонять все ключи с не-ASCII символами, либо свёртывать `unicode.ToUpper(unicode.ToLower(r))`. После этого проверять `strings.EqualFold(key, "address")` и т. д. Значения (`network`) сравнивать без учёта регистра.
- Отклонять объект, в котором два ключа сворачиваются в одно имя (см. находку 4).
- Лучше: после проверки перекодировать части в каноническую форму (ключи в нижнем регистре, без дублей) и отдавать ядру только её.
- Защита в глубину на Linux: запускать ядро от отдельного пользователя с ambient `CAP_NET_ADMIN`, либо хотя бы закрыть известные сокеты через `InaccessiblePaths=-/run/dbus -/run/systemd/private -/var/run/docker.sock` в юните.
- Тест: таблица вариантов регистра и свёртки для каждого проверяемого ключа и значения.

**Уверенность:** подтверждено. `Validate` пропускает такие ключи, а стандартный `encoding/json` сопоставляет их без учёта регистра. Какие именно outbound-ы xray принимают путь сокета в `address`, зависит от версии ядра; на вывод это не влияет.

## 2. [Высокая, Windows] Каталог лога службы в `%ProgramData%` может заранее создать пользователь

**Где:** `internal/service/run_windows.go:68-80` (`openServiceLog`).

**Суть.** Обычный пользователь может создавать подкаталоги в `C:\ProgramData`. Если `%ProgramData%\xray-runner` уже существует (создан до установки или между удалением и новой установкой), `MkdirAll` молча принимает его. Дальше SYSTEM делает `SetNamedSecurityInfo` (строка 75), а она проходит по точке повторного разбора, и `os.OpenFile(…, O_TRUNC)` (строка 79). Если на месте каталога junction, SYSTEM поставит защищённый DACL «только SY/BA» на чужой каталог и создаст или обрежет в нём `service.log`. Даже без junction владельцем каталога остаётся пользователь. Как владелец он всегда может вернуть себе `WRITE_DAC` и читать лог, где есть сессии других пользователей и вывод ядра. README обещает, что лог «читают только администраторы».

**Почему важно.** Это привилегированная операция над файлом по пути, который выбирает пользователь: от порчи DACL системных каталогов до записи текста, на который влияет пользователь, в произвольный `service.log`.

**Как исправить:**
- Создавать каталог при `service install` (у установщика права администратора) с явным дескриптором и владельцем SY/BA. Если каталог уже есть и его владелец не SY/BA, удалять его или отказываться.
- При запуске открывать каталог с `FILE_FLAG_OPEN_REPARSE_POINT` и проверять, что это не reparse point и владелец SY/BA, до любых операций над ним.
- Проще: писать лог в `%ProgramFiles%\xray-runner\log` (создаёт установщик) или в журнал событий Windows.

**Уверенность:** вероятно. Стандартный DACL `ProgramData` и поведение `SetNamedSecurityInfo` и `CreateFile` на junction хорошо известны; на живой Windows не проверял.

## 3. [Высокая, Linux] Split через службу не переживает обрыв соединения: приложения молча идут мимо туннеля

**Где:** `internal/app/remote.go:352-397` (`serviceSplit`), `internal/app/session.go:794-797` (`refreshSplit`), `internal/service/service.go:231-251` (`detach`).

**Суть.** Для TUN есть `watchRemote` и `reconnectService` с `Hello.Resume`. Для split на Linux (режим PROXY, `enable_split`/`refresh_split`) их нет. Токен из `SplitReply` сохраняется, но нигде не используется. Если соединение со службой обрывается (служба перезапущена по `Restart=on-failure`, переустановлена или соединение просто разорвалось), служба через 10 с снимает split: убирает nft-правила и возвращает процессы из cgroup. Интерфейс продолжает показывать split. Повторный скан каждую секунду получает `ErrClosed` и пишет его только на уровне Debug (`session.go:796`).

**Почему важно.** Приложения из списка незаметно начинают ходить напрямую с реальным адресом. Для VPN-клиента это утечка без единого сигнала.

Смежная проблема (подтверждено чтением): `a.service()` выбирается один раз при запуске (`useService`) и больше не пере-набирается. После перезапуска или обновления службы, пока интерфейс открыт, каждая новая TUN-сессия (`session.go:44` → `runRemoteSession`) падает с «соединение со службой закрыто», пока интерфейс не перезапустят.

**Как исправить:**
- Для split-сессии через службу запускать такой же наблюдатель, как `watchRemote`: пере-набирать с `Resume`. Если сессия не вернулась — `splitOff` с понятной ошибкой на экране статуса. Ошибку `refresh_split` показывать, а не прятать в Debug.
- В `service()` или перед `runRemoteSession`/`serviceSplit` пере-набирать соединение, если `Done()` уже закрыт.
- Тест: `fakeService`, у которого рвётся `Done()` во время split.

**Уверенность:** подтверждено чтением кода.

## 4. [Средняя] `noKernelTun` у wireguard перебивается ключом-двойником

**Где:** `internal/xraycfg/clientparts.go:351-379` (`userspaceWireguard`).

**Суть.** Служба дописывает только точный ключ `settings["noKernelTun"] = true`. Клиент может прислать двойника, например `"no\u212AernelTun": false` со знаком Кельвина. `json.Marshal` сортирует ключи map по байтам, поэтому двойник оказывается после `noKernelTun`. При разборе побеждает последний, и `encoding/json` получает `NoKernelTun=false`. Проверено: `AssembleService` выдаёт `{"noKernelTun":true,"noKernelTun":false}` (второй — с K), и стандартный разбор даёт `false`.

**Почему важно.** Ядро с `CAP_NET_ADMIN` поднимет wireguard в ядре. Комментарий в коде сам говорит, что такой интерфейс «никто не снимает». Журнал H06 про него тоже не знает.

**Как исправить:** удалять из `settings` все ключи, которые сворачиваются в `nokerneltun`, и только потом ставить свой. В общем виде — то же правило про дубли и канонизацию, что в находке 1.

**Уверенность:** подтверждено для `encoding/json` Go 1.26. Для конкретной сборки xray — вероятно: она разбирает JSON тем же пакетом.

## 5. [Средняя, Windows, решение по дизайну] Службой пользуется любой вошедший в систему пользователь

**Где:** `internal/ipc/transport_windows.go:237-246` (`authorize`), SDDL на строке 32 (`IU`), README «Служба / Windows».

**Суть.** На Linux доступ ограничен группой `xray-runner`, которую формирует администратор. На Windows проходит любой токен с `INTERACTIVE`: обычный пользователь, гость, пользователь RDP-сессии. До H10 для TUN нужны были права администратора.

**Почему важно.** Любой из них может:
- направить весь трафик машины, включая чужие сессии, через свой сервер: TUN на Windows общий для всей машины;
- включить kill switch на всю машину;
- получать строки лога ядра, где на уровнях debug/info видны адреса назначения трафика других пользователей.

На общем компьютере это новая граница доверия, и README о ней молчит.

**Как исправить:** при установке создавать локальную группу (например, `xray-runner Users`), добавлять в неё того, кто устанавливает, и проверять членство в `authorize`, как на Linux. Минимум — явно описать это в README.

**Уверенность:** подтверждено; это следствие дизайна.

## 6. [Средняя] Клиент, который не читает, блокирует службу: остановку, возврат сессии, а для владельца сессии — и саму службу

**Где:** `internal/ipc/server.go:55-81` (`writeLoop`), `server.go:127-148` (`send`/`Close`), `internal/service/service.go:411-419` (`emit`), `internal/app/servetun.go:105-117`.

**Суть.** Запись в сокет или канал идёт без таймаута. `Close()` закрывает `rw` только после выхода `writeLoop`, а тот висит в `Write`. Ответы и события `status`/`ended` не выбрасываются, а ждут места в очереди из 256 сообщений. Отсюда:
- `Serve` не возвращается: `wg.Wait()` ждёт `handle`, который висит в `Read`, а `rw` никто не закрывает. Проверено временным тестом: клиент шлёт `status` и не читает, `cancel()` — `Serve` не вернулся за 3 с. systemd добьёт службу через `TimeoutStopSec=30`, у SCM Windows служба зависнет в `StopPending`.
- `resume` → `old.Close()` не освобождает старое соединение (утечка горутин и дескрипторов).
- Если не читает владелец TUN-сессии (например, TUI приостановлен по Ctrl+Z), `emit` блокирует горутину-пересыльщик статусов в `ServeTun`. После остановки `defer` на `<-forwarded` не завершается, `sess.done` не закрывается, `s.sess` не обнуляется, и служба остаётся «занятой» для всех до перезапуска. Сеть при этом восстановлена: `releaseSession` выполняется раньше.

**Как исправить:**
- Дедлайн записи: `SetWriteDeadline` на `UnixConn`; на Windows — таймер плюс `CancelIoEx`.
- `Close()` закрывает `rw` после короткого ожидания слива очереди (сотни мс), а не после выхода `writeLoop`.
- Статус-события сделать выбрасываемыми или «последнее побеждает»: они всё равно перезаписывают друг друга.
- Тест: клиент, который не читает, при `Serve`, `resume` и завершении сессии.

**Уверенность:** подтверждено (зависание `Serve`); цепочка до «занятой» службы — вероятно, по чтению кода.

## 7. [Средняя, Linux] При запуске через сокет systemd права `/run/xray-runner` не выправляются

**Где:** `internal/ipc/transport_linux.go:109-114` (ранний возврат для `activated()`), `RuntimeDir` на строке 142, `internal/system/journal_linux.go:42`.

**Суть.** Журнал H06 создаёт `/run/xray-runner` с правами 0700, если запуск через `sudo` оказался там первым. `RuntimeDir()` исправляет права на 0755, но вызывается только в ветке без socket activation. systemd не меняет права уже существующего каталога (`DirectoryMode` действует только при создании). Сценарий: пользователь запускал `sudo xray-runner`, получил подсказку про службу и в той же загрузке сделал `service install`. Сокет оказывается внутри каталога 0700, члены группы получают `EACCES`, и интерфейс молча переходит в режим без службы, а TUN сообщает «нужны права».

**Почему важно.** Первая установка по подсказке программы не работает до перезагрузки.

**Как исправить:** вызывать `RuntimeDir()` и при socket activation: каталог принадлежит root, и `chmod` работает без `CAP_FOWNER`. Либо выправлять права в `install()` до `systemctl enable --now`. Тест на `Listen` с `LISTEN_FDS`.

**Уверенность:** вероятно.

## 8. [Средняя, Linux] Владелец порта перенаправления проверяется один раз и только для TCP

**Где:** `internal/service/service.go:526-533`, `internal/service/run_linux.go` (`listenerUIDIn` читает только `/proc/net/tcp`).

**Суть.** Владелец порта `RedirectPort` (TCP 10810) проверяется только при `enable_split`. Порт DNS `RedirectDNS` (UDP 10853, на него nft направляет DNS-запросы процессов из cgroup) не проверяется вовсе, и при `refresh_split` проверки нет. Если ядро интерфейса перезапускается (retry, смена сервера) или падает, в образовавшемся окне другой локальный пользователь может занять порт. Тогда трафик и DNS перенесённых процессов уходят к нему: он видит адреса назначения и может подменять DNS-ответы.

**Как исправить:** на каждом `refresh_split` (он и так раз в секунду) проверять владельцев обоих портов, TCP и UDP (`/proc/net/udp`). При чужом владельце снимать split и сообщать об этом.

**Уверенность:** вероятно (нужен враждебный локальный пользователь).

## 9. [Средняя] Гонка grace и resume: возвращённая сессия умирает без события `ended`

**Где:** `internal/service/service.go:242-250` (таймер grace), `service.go:210-229` (`resume`), `service.go:444-451` (`teardown`), `service.go:330` (подавление `ended`).

**Суть.** Таймер проверяет `orphan` под `mu`, отпускает мьютекс и вызывает `teardown`, который ставит `stopping`. `resume` не смотрит на `stopping`. Если клиент возвращается в этом окне или пока идёт сам `teardown` (у TUN это секунды: остановка ядра и снятие маршрутов), он получает `Resumed=true`. Затем сессия завершается с `stopping=true`, и событие `ended` не отправляется.

**Почему важно.** Интерфейс считает туннель поднятым: `watchRemote` ждёт `ended` или `Done`, а не приходит ни то, ни другое. При этом kill switch уже снят, и трафик идёт напрямую без предупреждения.

**Как исправить:**
- Решать «сиротство» и ставить `stopping` за одно удержание `mu`.
- `resume` отказывает сессии со `stopping`.
- `ended` подавлять только для того соединения, которое само запросило `stop`: хранить инициатора, а не общий флаг.

**Уверенность:** вероятно (узкое окно, по чтению кода).

## 10. [Низкая–средняя] `stop` выполняется параллельно с другими запросами того же соединения; поля сессии читаются без мьютекса

**Где:** `internal/service/service.go:188` (`go func() { … s.stop(c) }()`), чтение `sess.conn` без `mu` на строках 436, 513, 535, 564, 588; запись `sess.names` на строке 551.

**Суть.** `stop` для split-сессии идёт в отдельной горутине, а следующий `enable_split` того же соединения видит ещё живую сессию, переиспользует её и включает правила. Затем `teardown` обнуляет `s.sess`. Итог: nft-правила и cgroup включены, а сессии, которая их снимет, нет, и `disable_split` отвечает «нечего снимать». Подтверждено временным тестом (`DisableSplit` с задержкой 20 мс) уже на первой итерации. Честный интерфейс так не делает: для split он шлёт `disable_split`, который выполняется синхронно. Но это граница доверия, и такой клиент может быть багнутым или намеренно собранным. Правила доживут до следующего старта службы (`RecoverJournal`). Кроме того, `sess.conn` и `sess.names` читаются и пишутся без `s.mu`. Формально это гонки данных; race detector в тестах их не ловит из-за happens-before через соседние захваты `mu`.

**Как исправить:** сериализовать операции над сессией отдельным мьютексом сессии. `stop` выполнять синхронно в цикле `handle`, а асинхронной делать только отправку ответа. Все чтения `sess.conn` брать под `s.mu`.

**Уверенность:** подтверждено (состояние «правила без сессии»); гонки данных — по чтению кода.

## 11. [Низкая] `Serve` снимает сессию по снимку, пока обработчики ещё принимают запросы

**Где:** `internal/service/service.go:129-139`.

**Суть.** После выхода из `Accept` берётся снимок `s.sess` и снимается, но уже подключённые `handle` продолжают работать. `enable_split`, пришедший между снимком и `c.Close()`, заведёт новую сессию и включит правила уже после `teardown`, и служба завершится с ними. Для TUN это безопасно: контекст отменён.

**Как исправить:** флаг `closing` под `mu`; `claim` при нём отказывает; сначала закрыть соединения, потом снимать.

**Уверенность:** вероятно.

## 12. [Низкая, Linux] Владелец процесса проверяется до переноса (TOCTOU)

**Где:** `internal/system/split_linux.go:434` (`ownedBy`), перенос в `cgroup.procs` на строке 426 и далее.

**Суть.** Между чтением `/proc/<pid>/status` и записью pid в `cgroup.procs` процесс может завершиться, а его pid достаться процессу другого пользователя. Тогда в split и в перенаправление попадёт чужой процесс. Кроме того, setuid-потомки перенесённого процесса остаются в cgroup.

**Как исправить:** после записи ещё раз проверить владельца и вернуть процесс на место, если он чужой; либо использовать pidfd и проверять через него.

**Уверенность:** вероятно (окно узкое).

## 13. [Низкая] В лог владельца сессии пересылаются все строки лога службы, включая чужие

**Где:** `internal/service/run.go:131-141` (`teeHandler`), `internal/service/service.go:423-427` (`forwardLog`).

**Суть.** Владельцу сессии уходит весь `slog` службы: «подключился интерфейс user=…», причины отказов с именами пользователей и т. п. README говорит только про строки ядра.

**Как исправить:** пересылать только вывод ядра и строки своей сессии через отдельный логгер, а не весь глобальный `slog`.

**Уверенность:** подтверждено чтением кода.

## 14. [Низкая] До авторизации и в `Refuse` принимается сообщение до 4 МиБ; нет таймаута на hello и лимита соединений

**Где:** `internal/ipc/server.go:152-167` (`Refuse` читает hello через `ReadMessage`), `internal/ipc/proto.go:190-196` (`make([]byte, n)` до получения данных), `internal/service/service.go:154`.

**Суть.** Отвергнутый клиент может заставить службу выделить до 4 МиБ. Разрешённый клиент может держать сколько угодно соединений, объявив большой кадр и не отправив данные. На Linux чужих не пускают права сокета 0660, на Windows — DACL, так что это вопрос устойчивости.

**Как исправить:** в `Refuse` и для первого сообщения — предел в несколько КиБ и дедлайн чтения; ограничить число одновременных соединений.

**Уверенность:** подтверждено чтением кода.

## 15. [Низкая, Windows] `LookupAccount` в цикле `Accept`

**Где:** `internal/ipc/transport_windows.go:234`.

**Суть.** Поиск имени учётной записи для лога выполняется синхронно в `Accept`. Медленный ответ контроллера домена задерживает приём всех клиентов, и они получают `ERROR_PIPE_BUSY` или таймаут 3 с в `useService`, после чего молча переходят в режим без службы.

**Как исправить:** определять имя после `Accept` в горутине `handle` или лениво.

**Уверенность:** вероятно.

## 16. [Низкая, Windows] Имя канала можно занять, пока служба не запущена

**Где:** `internal/ipc/transport_windows.go:112-127`.

**Суть.** Клиент правильно отвергает такой канал: владелец не SY/BA. Но служба с `FILE_FLAG_FIRST_PIPE_INSTANCE` не стартует, а после трёх попыток SCM сдаётся. Это отказ в обслуживании со стороны любого пользователя, например в окне после падения службы.

**Как исправить:** писать в лог понятную причину и, по возможности, кто владеет каналом; упомянуть в README.

**Уверенность:** вероятно.

## 17. [Низкая, hardening] Опции сокета из конфига клиента применяются с `CAP_NET_ADMIN`/`CAP_NET_RAW`

**Где:** `internal/xraycfg/clientparts.go` (проверки `sockopt` нет).

**Суть.** `sockopt.mark`, `interface` и `customSockopt` (произвольный `setsockopt`) проходят проверку и применяются ядром с правами службы. Через `mark` клиент может совпасть с метками правил самой службы (маршрут в обход туннеля, kill switch). Глубоко не проверял.

**Как исправить:** допускать в `sockopt` только известные безвредные ключи, а `mark` и `customSockopt` отклонять.

**Уверенность:** вероятно.

## 18. [Низкая] Совместимость: гео-базы службы застывают на момент установки; холодный старт службы дольше 3 с

**Суть.**
- `u` в интерфейсе обновляет гео-базы только в папке пользователя. TUN через службу продолжает работать на старых базах из `InstallDir`, и правила могут вести себя не так, как в режиме PROXY, или ядро отвергнет категорию `geosite`, которой в старой базе нет. Обновить базы службы можно только повторным `service install`.
- `useService` ждёт hello 3 с (`remote.go:70`). При первом обращении служба стартует через сокет systemd, выполняет `xray version` и `RecoverJournal`, и на медленной машине может не успеть. Тогда интерфейс молча уходит в режим без службы.

**Как исправить:** сказать в README, что после `u` нужен повторный `service install`, или показывать версию баз службы. Таймаут hello поднять до 10 с, либо при ошибке TUN «нет прав» один раз повторять `useService`.

**Уверенность:** вероятно.

## Режим без службы

По коду не сломан:
- `XRAY_RUNNER_NO_SERVICE=1` и любая ошибка `dial` оставляют прежние функции `enableSplit`/`rescanSplit`/`disableSplit` и проверку прав;
- `runSession` идёт в `runRemoteSession` только при `a.service() != nil`;
- `TestNoServiceKeepsLocalRights` это покрывает.

Оговорки — находки 3 (мёртвое соединение не пере-набирается), 7 и 18 (молчаливый уход в режим без службы). Журнал H06: служба на Linux пишет в `/run/xray-runner` (он есть в `ReadWritePaths`), на Windows — в HKLM, туда же, куда запуск через `sudo` или от администратора. При старте `RecoverJournal` не трогает запись живого процесса. Совместимо.

## Каких тестов не хватает

1. `Validate`/`AssembleService`: варианты регистра и Unicode-свёртки для `address`, `redirect`, `dest`, `server`, `network`; ключи-двойники (`noKernelTun`); `sockopt`.
2. IPC: клиент, который не читает, при `Serve`, `resume` и завершении сессии; таймаут hello; кадр 4 МиБ в `Refuse`.
3. Служба: `resume` во время `teardown` или на истечении grace; `stop` и `enable_split` подряд из одного соединения; `enable_split` во время остановки `Serve`; тесты на гонки данных под `-race` с медленными `Deps`.
4. Интерфейс: обрыв соединения во время split на Linux; соединение, умершее между сессиями (пере-набор перед `runRemoteSession`).
5. Linux: `Listen` при socket activation, когда `/run/xray-runner` уже есть с правами 0700; `listenerUID` для UDP; повторная проверка владельца порта при `refresh_split`.
6. Windows (unit, в CI уже есть `windows-latest`):
   - `pipeConn`: одновременные `Read`/`Write`/`Close` (цикл `CancelIoEx`), `Close` при висящей записи;
   - `authorize` для не-интерактивного токена;
   - создание каталога лога, когда он уже существует, принадлежит пользователю или является junction.
7. e2e Windows: вторая пользовательская учётная запись (отказ или «занято»), обрыв и возврат сессии, лог службы недоступен обычному пользователю.
